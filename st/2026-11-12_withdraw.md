# 코드 리뷰: 회원 탈퇴

- 날짜: 2026-11-12
- 브랜치: `feature/42_withdraw` (이슈 #42)
- 기능: F1-8(회원 탈퇴)
- 결정: Q-7 결정(revoke 실패 시 탈퇴 중단, 사용자 결정), Q-25 신설(탈퇴 때 재인증으로 제공자 토큰 확보, 사용자 결정), ADR-0002·0004·0005 갱신

## 배경
로그인은 `openid` 범위만 받고 Google 토큰을 저장하지 않아, 탈퇴 때 revoke할 제공자 토큰이 없었다. 토큰을 저장하는 대신 탈퇴할 때 계정 선택 화면(`prompt=select_account`)을 한 번 더 거쳐 새 Access Token을 받고, 그 토큰으로 revoke한 뒤 회원을 지운다.

흐름: `POST /users/me/withdrawal`(Access) → `{ redirect_url }` → 브라우저가 Google 재인증 → `GET /auth/google/withdraw/callback` → 계정 일치 확인 → revoke → 회원 삭제(관심 분야·북마크는 FK CASCADE) → 모든 세션 폐기 → `FRONTEND_WITHDRAW_REDIRECT_URL?withdrawn=true`.

### 권장
1. **배포 전 할 일: Google 콘솔에 콜백 등록** — `GOOGLE_WITHDRAW_REDIRECT_URI`(기본 `http://localhost:8000/auth/google/withdraw/callback`, 운영 주소도)를 Google 콘솔의 승인된 리디렉션 URI에 추가해야 한다. 없으면 Google이 `redirect_uri_mismatch`로 막는다. 프론트는 `FRONTEND_WITHDRAW_REDIRECT_URL`(기본 `/withdraw/callback`) 페이지에서 `withdrawn`·`error`를 처리해야 한다.
2. **revoke 성공 뒤 DB 삭제가 실패하는 경우** — `app/auth/service.py`의 `complete_withdrawal`은 revoke → 삭제 순서라, revoke 직후 DB 오류가 나면 Google 연결만 끊기고 계정은 남는다(500). 그래도 다시 로그인하면 동의를 받고 같은 회원으로 돌아오므로 데이터가 사라지지 않는다. 순서를 반대로 하면 Q-7(revoke 실패 시 지우지 않음)을 지킬 수 없어 이 순서를 택했다.
3. **배포 전에 발급된 세션** — 회원별 세션 목록 `user_families:{user_id}`는 이 변경 이후 Refresh를 저장할 때부터 쌓인다. 배포 뒤 한 번도 재발급하지 않은 세션의 Access(최대 15분)는 탈퇴 직후에도 서명만으로 통과한다. Refresh는 회원이 없어 거절되고 `GET /users/me`도 401이지만, 그 짧은 사이 `PUT /contests/{id}/bookmark`는 FK 위반으로 500이 날 수 있다. 15분 뒤에는 생기지 않는 일이라 따로 처리하지 않았다.
4. **Kakao** — F1-6 Kakao가 아직 없어 탈퇴도 Google만 구현했다. Kakao는 Admin 키로 `unlink`할 수 있어 재인증이 필요 없을 수 있으니, F1-6 Kakao 때 `OAuthProvider` 계약을 다시 본다.
5. **회원 id로 막지 않은 이유** — 처음에는 `user_revoked:{user_id}` 표식을 검토했지만, id를 다시 쓰는 DB(테스트용 SQLite)에서 탈퇴 직후 가입한 새 회원까지 막혀 세션(family) 단위 폐기로 바꿨다. 기존 `revoke_family`와 인증 시 `EXISTS` 조회를 그대로 쓴다.

### 확인한 것
- 명세: F1-8 수용 기준(계정·프로필·관심 분야·북마크·토큰 삭제, OAuth 연결 해제) 구현, 상태 `done`. Kakao는 F1-6과 함께 남음으로 적었다.
- 결정: 열려 있던 Q-7은 사용자에게 물어 `결정됨`으로 바꿨다. 토큰 확보 방식은 Q-25로 남겼다. ADR-0004 엔드포인트 초안의 `DELETE /users/me`를 실제 흐름으로 바꾸고 에러 코드를 적었다. ADR-0005에 Redis 키 두 개, ADR-0002에 회원별 세션 목록을 더했다.
- 아키텍처: 제공자 호출은 `OAuthProvider` 계약(`withdraw_authorization_url`·`exchange_withdraw_code`·`revoke`) 뒤에 두었다. 라우터는 service만 부르고, Redis·DB 접근은 repository에만 있다. AC-1~3 유지. `complete_withdrawal`은 복잡도 10 이하(ruff C90 통과).
- 보안: state는 32바이트 무작위 값이고, 회원 id와 묶어 10분 동안 서버에 둔 뒤 GETDEL로 한 번만 쓴다. 재인증한 계정이 탈퇴를 요청한 회원과 다르면 거절하고 그 계정의 연결은 끊지 않는다. 그래서 공격자가 자기 탈퇴 주소를 피해자에게 보내도 피해자 계정은 지워지지 않는다. `OAuthGrant.access_token`은 `repr=False`. 앱 로그에는 user_id·provider만 남는다. 콜백 쿼리의 `code`·`state`는 기존 `log_redaction`이 접근 로그에서 가린다. 콜백 응답은 `Cache-Control: no-store`.
- 주석: 새로 쓰거나 고친 모듈·클래스·함수 모두 한 줄 docstring.
- 테스트: `test_withdraw.py` 13건(성공 시 revoke·개인 데이터 삭제, 모든 기기 토큰 401, 재가입, revoke 장애·거절 시 유지, 다른 계정, 취소, state 없음·모름·재사용, 토큰 없이 시작, 로그에 토큰 없음), `test_google_oauth.py` 5건(탈퇴 주소, 탈퇴 콜백 주소로 교환, revoke 요청 형식, revoke 실패 예외). 테스트 SQLite에 `PRAGMA foreign_keys=ON`을 켜 CASCADE를 실제로 확인한다. 네트워크 호출 없음.
