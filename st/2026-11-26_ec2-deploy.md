# 코드 리뷰: develop 머지 시 EC2 자동 배포

- 날짜: 2026-11-26
- 브랜치: `feature/76_ec2-deploy` (이슈 #76)
- 기능: 없음 (프로젝트 설정)
- 결정: Q-37 결정됨. 배포 대상 EC2 한 대, develop 머지 때 자동 배포, PostgreSQL·Redis는 같은 EC2의 Docker, SSH는 배포 동안만 러너 IP 개방 (2026-11-26 사용자 결정)

## 배경
CI(`ci.yml`)와 Docker Hub push(`image.yml`, #64)는 이미 있었다. 남은 것은 Q-37의 열린 부분인 배포 대상과 배포 워크플로였다.

## 바뀐 것
- `.github/workflows/deploy.yml` 추가: `image` 워크플로가 develop에서 성공하면(`workflow_run`) 그 커밋의 `sha-<7자리>` 이미지를 배포한다. 수동 실행에 태그를 넣으면 롤백이다. 순서: 설정 확인 → 태그 계산(문자 검사) → 같은 커밋 checkout → 보안 그룹 22 포트에 러너 IP/32 등록(이전 실행이 남긴 규칙은 먼저 지움) → 미리 받아 둔 호스트 키로만 SSH → compose·스크립트 복사 → `deploy.sh` 실행 → (선택) `HEALTH_URL` 확인 → 규칙·키 삭제(`always()`). 동시 실행은 `concurrency: deploy`로 하나씩.
- `deploy/docker-compose.yml` 추가: 운영 compose(프로젝트 `comp-prod`). PostgreSQL·Redis는 호스트 포트 없음, `POSTGRES_PASSWORD` 필수, migrate는 `run`으로만 돈다.
- `deploy/deploy.sh` 추가: 이미지 받기(비공개 저장소면 표준 입력 토큰으로 로그인 후 바로 로그아웃) → DB 기동 → 마이그레이션 → API 교체(`--wait`, 실패 시 로그 출력) → `release.env`에 마지막 성공 배포 기록 → 3일 지난 미사용 이미지 정리.
- `ci.yml` image 잡: `shellcheck deploy/deploy.sh`, 방금 빌드한 이미지로 운영 compose + `deploy.sh`를 실제로 돌려 `/health`와 `release.env`를 확인.
- `docs/decisions.md` Q-37, `README.md` 'EC2 자동 배포'(서버 준비, IAM 정책, Secrets/Variables 표).

### 권장
- 머지 전에 README의 EC2 준비·IAM·Secrets/Variables를 끝낸다. 없으면 develop 머지 때마다 deploy 워크플로가 첫 단계에서 실패로 표시된다(이미지 push에는 영향 없음).
- 지금은 http(8000)로만 노출된다. Q-41의 `Secure` 쿠키와 운영 프론트를 생각하면 리버스 프록시(Caddy·nginx)와 인증서를 다음 작업으로 정한다(Q-37에 열림으로 남김).
- `deploy.sh`는 API가 healthy가 되지 않아도 자동 롤백하지 않는다(마이그레이션 뒤라 이전 버전이 맞는다는 보장이 없음). 실패하면 수동 실행으로 이전 태그를 배포한다.
- 알림 발송 CLI(`app/notifications/dispatch.py`)의 정기 실행은 이 PR 범위 밖이다.
- 장기 AWS 키 대신 GitHub OIDC 역할로 바꿀 수 있다(`configure-aws-credentials`의 `role-to-assume`).

### 확인한 것
- 명세: 기능 변경 없음. Python 코드 변경 없음.
- 결정: Q-37의 "마이그레이션은 기동 때 자동 실행하지 않고 배포마다 API보다 먼저"를 `deploy.sh`가 지킨다.
- 아키텍처: 앱 코드 변경 없음.
- 보안: 비밀 값은 Secrets와 서버 `.env`에만 있고 이미지·저장소에 없다. Docker Hub 토큰은 명령줄이 아니라 표준 입력으로 넘기고 받은 뒤 로그아웃한다. 원격 명령에 들어가는 태그는 정규식으로 검사한다. 호스트 키는 고정값(`StrictHostKeyChecking yes`). 22 포트는 배포 동안만 /32로 열고, IAM은 그 보안 그룹 규칙만 고칠 수 있다. `workflow_run`은 기본 브랜치의 워크플로 정의로 돌아 포크 PR이 비밀을 쓸 수 없다. 권한은 `contents: read`.
- 주석: 워크플로·compose·스크립트 머리말에 필요한 설정과 이유를, 단계마다 왜를 적었다.
- 테스트: CI image 잡이 `deploy.sh`를 운영 compose로 실제 실행한다. 로컬에서 첫 배포, 재배포, 마이그레이션 실패(잘못된 DB 비밀번호 → 종료 코드 1, 기존 API는 `/health` 200 유지)를 확인했다.
- 발견해서 고친 것: 처음에 운영 compose의 프로젝트 이름이 로컬 개발용과 같은 `comp`여서 로컬 PostgreSQL·Redis 컨테이너를 덮어썼다(볼륨은 그대로, 바로 복구). `comp-prod`로 바꿨다. 또 이미지 정리가 개발자 PC에서도 돌아 `SKIP_PULL=1`이면 건너뛰게 했다.
- Git 규약: 이슈 #76, `feature/76_ec2-deploy`, 커밋 `⚙️`.
