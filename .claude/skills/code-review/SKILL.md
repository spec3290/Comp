# 코드 리뷰

머지 조건은 **최소 1명의 approve + CI 성공**이다. 이 스킬은 approve 여부를 판단할 근거를 만든다.
린트·타입·아키텍처·테스트는 CI가 이미 검사하므로 중복해서 읽지 말고, 사람이 봐야 하는 것에 집중한다.

## 절차

1. `gh pr checks <번호>`로 CI 상태를 확인한다. 실패했으면 원인부터 보고하고 나머지 리뷰는 보류한다.
2. `gh pr view <번호>`와 `gh pr diff <번호>`로 변경을 읽는다. 연결된 이슈와 기능 ID를 확인한다.
3. 아래 점검표를 순서대로 본다.
4. 결과를 출력 형식대로 보고한다. 요청이 있을 때만 `gh pr review`로 남긴다.

## 점검표

**명세 일치** — 연결된 기능의 [수용 기준](../../../docs/features.md)이 모두 구현됐는가? MVP 밖 기능이 섞이지 않았는가? features.md의 상태가 바뀌었는가?

**결정 준수** — [decisions.md](../../../docs/decisions.md)에서 `열림`인 Q-항목을 추측으로 구현하지 않았는가? ADR-0004 에러 포맷, ADR-0005 데이터 원칙(상태는 계산)을 지켰는가? 구조·API·데이터 모델이 바뀌었으면 ADR이 같이 고쳐졌는가?

**아키텍처** — CI가 못 잡는 설계 문제: 서비스가 너무 많은 일을 하는가, 도메인 규칙이 라우터·리포지토리로 새지 않았는가, 트랜잭션 경계가 유스케이스 하나인가, 구현체가 여러 개인 외부 경계(크롤러·OAuth)를 Protocol 뒤에 두었는가 (ADR-0007). 린트·계약을 약화하거나 `# noqa`, `# type: ignore`, `ignore_imports`를 새로 넣었다면 이유가 타당한가.

**정확성·보안**
- 시간: naive `datetime` 없음, KST 경계(마감 당일, 자정) 처리, 접수 상태를 저장하지 않고 계산.
- 인증: 만료·위조·블랙리스트·회전된 Refresh가 401, Refresh 재사용 시 family 폐기, 로그·응답에 토큰·개인정보 없음.
- 입력 검증, SQL 조립 없음, 비밀 값 하드코딩 없음, 탈퇴 시 데이터 삭제와 OAuth 연결 해제.
- 크롤링: 실패 시 기존 데이터 유지, 부분 실패 격리, 멱등 upsert, 요청 간 지연.

**테스트** — 수용 기준 항목마다 테스트가 있는가? `@pytest.mark.feature`가 달려 있는가? 경계값과 실패 경로가 있는가? 실제 네트워크를 호출하지 않는가?

**Git 규약** — 커밋 메시지·브랜치·PR 제목이 [git-workflow](../git-workflow/SKILL.md)를 따르는가? 한 PR이 한 이슈에 대응하는가?

## 출력 형식

```
## 리뷰 결과: <approve | 수정 요청 | 보류(CI 실패)>

### 반드시 수정 (blocker)
- `파일:줄` 문제 → 이유 → 제안

### 권장
- ...

### 확인한 것
- 명세 / 결정 / 아키텍처 / 보안 / 테스트 / Git 규약 각 한 줄
```

blocker가 하나라도 있으면 approve하지 않는다. 취향 차이는 권장으로만 적는다. 근거 없이 "좋아 보인다"고 쓰지 않고, 읽은 파일과 점검한 항목을 `확인한 것`에 남긴다.
